1. Executive Summary
NutriAI is an AI-powered diet recommendation and food tracking platform that differentiates itself through a vision-first approach: users photograph their meals, and a Vision AI model identifies the food items, estimates serving sizes, and matches them against a curated food database. The system automatically calculates nutritional values and updates daily progress in real time. This document provides the complete system design blueprint for building NutriAI as a simplified, self-contained, production-ready system.
The original NutriAI specification was designed for a large-scale cloud deployment using AWS (ECS, RDS, S3, ElastiCache, CloudWatch), React Native mobile apps, JWT-based authentication, PostgreSQL with Redis caching, and Firebase push notifications. This blueprint re-architects the entire system for a dramatically simpler deployment footprint while preserving all core AI and nutritional intelligence capabilities.
Key architectural simplifications include: replacing PostgreSQL with MySQL accessed through Prisma ORM for type-safe database operations; replacing JWT/OAuth authentication with simple session-based auth using express-session stored in MySQL; replacing AWS S3 with local disk storage managed by Multer for food image uploads; removing Redis, Firebase, and all AWS infrastructure dependencies; and replacing the React Native mobile app with a responsive React web application using Tailwind CSS.
Most critically, this blueprint introduces a new feature not present in the original specification: the Unknown Food Auto-Add capability. When a user uploads a food photograph that the Vision AI successfully identifies but that does not exist in the food database, the system prompts the user to confirm the food name, specify the portion size, and provide or confirm nutritional values. The food is then automatically added to the database as a new cooked food entry, making it immediately available for all users. This feature enables the food database to grow organically through user contributions, significantly reducing the initial data population burden.
The system retains only two AI models: GPT-4o Vision (via OpenAI API) for food recognition from images, and a locally hosted Qwen 2.5 3B Instruct model (via Ollama) for meal ranking from pre-filtered candidate lists. All nutritional calculations (BMI, BMR, TDEE, macro distribution, meal filtering, scoring) remain deterministic backend algorithms that operate at database query speed without any AI involvement.
2. System Architecture Overview
The simplified NutriAI architecture follows a clean three-tier design pattern: a React single-page application as the frontend, a single Express.js server as the backend API, and a MySQL database as the persistence layer. Two external AI services (GPT-4o Vision API and a local Ollama instance running Qwen 2.5 3B) are accessed through dedicated adapter modules within the backend. This architecture eliminates the need for any cloud infrastructure beyond the single server hosting the application.

4. Authentication System (Simple Session-Based)
The authentication system uses express-session with a MySQL session store, providing a straightforward and reliable mechanism for managing user sessions without the complexity of JWT tokens, refresh token rotation, or OAuth integration. This approach is ideal for a web application where the frontend and backend share the same domain. Sessions are stored server-side in a MySQL table managed by express-mysql-session, with only a signed session cookie sent to the client browser.
4.1 Session Configuration
The session middleware is configured with the following parameters: the session secret is loaded from the SESSION_SECRET environment variable (a minimum 32-character random string generated at deployment time), the cookie is configured with httpOnly: true and sameSite: 'lax' to prevent cross-site request forgery and cross-site scripting attacks, the session maximum age is set to 7 days (604800000 milliseconds), and the rolling option is enabled to refresh the session expiry on each request, keeping active users logged in indefinitely.

4.3 Security Measures
Password security uses bcrypt with a cost factor of 12 salt rounds, providing approximately 250ms per hash computation on modern hardware. Login attempts are rate-limited to 10 requests per 15 minutes per IP address using express-rate-limit with a sliding window. Helmet.js is applied as global middleware to set 15 security-related HTTP headers including Content-Security-Policy, X-Frame-Options DENY, and X-Content-Type-Options nosniff. CORS is restricted to the frontend origin only. All API endpoints use Zod schemas for request validation, rejecting malformed input before it reaches any service layer.
5. Database Design (Prisma Schema for MySQL)
The database schema comprises 18 models organized into five logical groups: User Management, Food Database, Daily Tracking, Recommendations, and System. All models use auto-incrementing integer primary keys (optimized for MySQL), DateTime fields for timestamps, and explicit indexing on query-critical columns. The schema is designed for Prisma ORM with MySQL as the database provider, leveraging Prisma's type-safe query builder for all database operations.

6. Backend Service Architecture
The NutriAI backend is organized as a modular monolith with 11 specialized services, each following a Controller-Service-Repository layered architecture. This approach keeps the codebase maintainable and testable while allowing future extraction into microservices if scaling demands require it. All services share a single Express.js process and communicate through direct function calls with well-defined TypeScript interfaces.

6.2 Service Dependency Matrix
The dependency matrix below shows which services call which other services. The AuthService is a dependency for all user-facing services, as the authentication middleware protects all routes except login and register. OnboardingService is the most interconnected service, orchestrating UserService, NutritionEngineService, and MealPlanService during the user onboarding sequence. FoodRecognitionService depends on FoodDatabaseService for alias matching after Vision AI returns results, and on the new UnknownFoodService when a recognized food is not found in the database.

When FoodRecognitionService identifies a food item via Vision AI with confidence above 0.7 but FoodDatabaseService cannot find a matching entry in the database, the flow is redirected to UnknownFoodService. This service manages the multi-step user confirmation process, creates the new Meal and associated records (MealNutrition, MealAlias, MealServing), and then returns the newly created food to FoodRecognitionService for immediate logging in the user's food log.
7. AI Architecture
A core design principle of NutriAI is the deliberate minimization of AI model usage. The platform requires exactly two AI models, each with a narrowly scoped responsibility. This approach dramatically reduces infrastructure costs, lowers latency, improves reliability, and makes the system easier to debug and maintain. All nutritional calculations, meal filtering, scoring, and progress analysis are implemented as deterministic backend algorithms.
7.1 AI-1: Vision AI (GPT-4o via OpenAI API)
The Vision AI is responsible exclusively for identifying cooked food items from user-uploaded images. It receives a food photograph (as a base64-encoded image buffer, not a URL) and returns a structured JSON response containing the identified food name, estimated serving size in grams, and a confidence score between 0.0 and 1.0. The Vision AI does NOT calculate nutritional values, recommend meals, or make dietary judgments. Its output is simply a food identifier that the backend uses to look up nutrition data from the MySQL meal database via Prisma.
Vision AI System Prompt:You are a food recognition assistant for a diet tracking application. Your ONLY task is to identify cooked food items visible in the image. Follow these rules strictly: (1) Recognize ONLY cooked/prepared foods. Ignore raw ingredients, packaged items, and non-food objects. (2) Estimate the serving size in grams based on the visible portion. (3) Provide a confidence score (0.0 to 1.0). (4) Return ONLY valid JSON. (5) Do NOT calculate nutritional values. (6) Do NOT recommend alternative foods. (7) Use common, standardized food names. (8) For multi-item plates, identify each item separately. Return format: { "foods": [{ "name": "...", "serving_description": "...", "serving_weight_grams": N, "confidence": N.N }] }
7.2 AI-2: Meal Recommendation AI (Local Qwen 2.5 3B via Ollama)
The Meal Recommendation AI is a lightweight language model responsible for ranking pre-filtered meal candidates. It runs locally via Ollama, eliminating per-call API charges entirely. The model receives a filtered list of up to 20 candidate meals along with the user's nutritional goals, remaining calorie/protein budget, 7-day consumption history, and stated preferences. It returns a ranked list of exactly three meals with fit scores. The model does NOT perform any nutrition calculation, food recognition, or database operations. It is purely a ranking function that considers user preferences and variety constraints.
Meal Recommendation Prompt:You are a meal ranking assistant. Given the context, rank the candidates and return the top 3: User Goal: {goal}, Remaining Nutrition: {calories} kcal, {protein}g protein, {carbs}g carbs, {fat}g fat, Candidates: {candidates}, Recent History: {history}. Ranking criteria: (1) Macro fit: How well does the meal fit the remaining budget? (2) Variety: Prefer meals NOT consumed in the last 7 days. (3) Preference match: Prioritize matching cuisine. (4) Balance: Do not exceed calorie budget by more than 15%. Return ONLY JSON: { "recommendations": [{ "meal_id": N, "name": "...", "fit_score": N.N }] }
8. Vision AI Food Recognition Pipeline
The food recognition pipeline is the most complex user-facing flow in NutriAI, orchestrating image capture, upload, AI processing, database matching, and user confirmation into a seamless experience. The entire pipeline completes in under 5 seconds on a standard broadband connection. When a food is not found in the database, the new Unknown Food Auto-Add feature is triggered (detailed in Section 9).
8.1 Pipeline Steps
(1)  User captures/selects food photo via React upload component
(2)  Client-side: compress image (max 2MB, quality 0.7, max 1024px, JPEG)
(3)  POST /api/food-recognize with multipart/form-data (image file)
(4)  Multer saves image to /uploads/{uuid}.jpg with metadata validation
(5)  Backend reads saved file, converts to base64 buffer
(6)  Build system prompt + image payload for GPT-4o Vision API
(7)  Call OpenAI API with timeout of 15 seconds
(8)  Parse JSON response: { foods: [{ name, serving_description, serving_weight_grams, confidence }] }
(9)  Validate confidence >= 0.7 for each detected food item
(10) Normalize food name: lowercase, trim, remove quantity prefixes
(11) Alias matching: exact match against meal_aliases table (case-insensitive)
(12) Keyword extraction: remove 'plate of', 'bowl of', 'serving of' and re-match
(13) DB lookup: Fetch Meal + MealNutrition from Prisma
(14) IF food NOT found AND confidence >= 0.7 --> trigger Unknown Food flow (Section 9)
(15) IF food NOT found AND confidence < 0.7 --> return 'unrecognized' with manual search suggestion
(16) Return: { meal_id, name, serving, calories, protein, carbs, fat, confidence }

9. NEW FEATURE: Unknown Food Auto-Add to Database
This is a completely new feature that does not exist in the original NutriAI specification. When a user uploads a food photograph that the Vision AI successfully identifies with a confidence score of 0.7 or higher, but the identified food item cannot be found in the database through any alias matching strategy, the system initiates a multi-step interactive flow that allows the user to add the food as a new entry in the database. This feature enables the food database to grow organically through real user contributions, dramatically reducing the initial data population burden and ensuring the system can handle regional, home-cooked, and culturally specific foods that may not exist in any standard food database.

When the user confirms the unknown food details, the UnknownFoodService performs the following database operations in a single Prisma transaction to ensure atomicity. 10. Nutrition Engine
The Nutrition Engine is the scientific core of NutriAI, implementing well-established formulas from sports nutrition and clinical dietetics. All calculations are deterministic, fast (sub-millisecond), and require no AI involvement. The engine is invoked during onboarding, when user profile changes, and whenever the activity level or goal is updated. This section provides the exact formulas and lookup tables used by the NutritionEngineService.
10.1 BMI Calculation
Body Mass Index is calculated using the standard formula: BMI = weight_kg / (height_m * height_m). The resulting value is classified according to the World Health Organization categories: Underweight (BMI < 18.5), Normal weight (18.5 - 24.9), Overweight (25.0 - 29.9), and Obese (BMI >= 30.0). This classification is displayed to the user during onboarding and on the progress screen to provide contextual feedback about their current body composition status.
10.2 BMR Calculation (Mifflin-St Jeor Equation)
The Mifflin-St Jeor equation is considered the most accurate estimation formula for BMR in clinical practice. The formulas are gender-specific: Male: BMR = (10 * weight_kg) + (6.25 * height_cm) - (5 * age) + 5. Female: BMR = (10 * weight_kg) + (6.25 * height_cm) - (5 * age) - 161. For users selecting 'Other' gender, the system calculates both formulas and returns the arithmetic average. For example, a 28-year-old male weighing 75 kg at 175 cm would have: BMR = (10 * 75) + (6.25 * 175) - (5 * 28) + 5 = 750 + 1093.75 - 140 + 5 = 1708.75 kcal/day.
10.3 TDEE and Target Calorie Adjustment
Total Daily Energy Expenditure is calculated by multiplying the BMR by an activity multiplier. The multipliers are: Sedentary (1.2), Lightly Active (1.375), Moderately Active (1.55), Very Active (1.725), and Extra Active (1.9). Target calories are then adjusted based on the user's fitness goal: Muscle Gain (TDEE + 500), Lose Fat (TDEE - 500), Maintain (TDEE), Recomp (TDEE - 250), Weight Gain (TDEE + 750), and Athlete (TDEE + 300). Macro grams are calculated as: protein grams = (target_calories * protein_percentage) / 4, carbs grams = (target_calories * carbs_percentage) / 4, fat grams = (target_calories * fat_percentage) / 9.
10.4 Meal Distribution Logic
The user's total daily calorie and macro targets are distributed across four meal slots using default percentages: Breakfast (25%), Lunch (30%), Dinner (30%), and Snack (15%). When a user logs a meal, the remaining calorie and macro budget is dynamically redistributed proportionally across the remaining meal slots. For example, if the user consumes 700 kcal at breakfast (exceeding the planned 550 kcal), the remaining 1,650 kcal is redistributed proportionally across Lunch, Dinner, and Snack. The recalculation also adjusts macro targets proportionally.
11. Recommendation Engine Algorithm
The Recommendation Engine is a pure backend algorithm (NOT an AI model) that processes the meal database through a deterministic, multi-stage filtering and scoring pipeline to produce 20 candidate meals. These 20 candidates are then passed to the Meal Recommendation AI (local Qwen 2.5 3B) for final ranking and selection of the top 3 meals presented to the user.

11.2 Scoring Formula
Each candidate meal receives a composite score (0-100) calculated using the weighted formula: fit_score = (macro_fit * 0.50) + (variety_score * 0.30) + (preference_score * 0.20). The macro_fit component measures how closely the meal's nutritional profile matches the remaining calorie budget for the current slot, with a penalty applied if protein falls below 70% of the slot target. The variety_score rewards meals not consumed in the last 7 days (100 if never consumed, scaled linearly by days since last consumption). The preference_score assigns 100 points for cuisine match, 70 for neutral (Mixed preference), and 40 for mismatch. This weighted formula prioritizes nutritional accuracy (50%) while still considering meal variety (30%) and user preference alignment (20%).

13. Image Upload System (Local Disk + Multer)
Image storage has been completely simplified from the original AWS S3 + presigned URL architecture. The new system uses Multer middleware for handling multipart/form-data uploads directly through Express, storing files on the local filesystem in an /uploads directory served statically. This eliminates all external storage dependencies, reduces latency (no network round-trip to S3), and has zero recurring cost.
13.1 Multer Configuration
The Multer middleware is configured with the following settings: file size limit of 2MB (hard limit), allowed MIME types restricted to image/jpeg and image/png, file filter that rejects non-image files with a clear error message, destination directory set to /uploads relative to the project root, and a custom filename function that generates UUID-based filenames with the .jpg extension to prevent conflicts and support concurrent uploads. The uploaded file is stored locally, and its relative path is returned to the client for reference.
13.2 Static File Serving
Uploaded images are served statically via Express: app.use('/uploads', express.static('uploads')). This allows the frontend to display food images using simple URL paths like /uploads/{uuid}.jpg. For production, Nginx should be configured to serve the /uploads directory directly, bypassing the Express process for better performance. A cleanup cron job (optional) can be configured to delete images older than 30 days, as food photographs are not needed long-term after the recognition is complete and the food has been logged.

16. Error Handling and Logging
The error handling framework provides consistent, machine-readable error responses across all API endpoints. Every error is categorized by domain, assigned a unique numeric code, and includes a human-readable message and an ISO 8601 timestamp. The framework supports graceful degradation: when a non-critical component fails, the system continues to function with reduced capability rather than returning a 500 error to the user.
16.1 Error Code Registry
16.2 Graceful Degradation
When a non-critical dependency fails, specific fallback behaviors are implemented. If Vision AI times out (no response within 15 seconds), the system returns an empty recognition result and prompts the user to manually search for their food. If the Meal Recommendation AI is unavailable (Ollama server down), the system falls back to pure deterministic scoring using the weighted composite formula, producing slightly less personalized but still functional recommendations. If image upload fails, the client caches the compressed image locally and retries on the next interaction.
16.3 Logging Configuration
Logging is implemented with Winston in structured JSON format. Every log entry includes a timestamp, log level (error, warn, info, http, debug), request ID (generated per request), service context, and optional metadata fields. In production, logs are written to both a rotating file transport (with 14-day retention and 10MB max file size) and the console. Error-level logs are always written. The logging system redacts sensitive fields (passwords, email addresses are partially masked as u***@domain.com) to prevent data leakage in log files.
17. Deployment Guide
The simplified NutriAI system is designed for deployment on a single Virtual Private Server (VPS) or any Linux server with at least 2GB RAM and 2 CPU cores. This section provides complete deployment instructions for both development and production environments.
17.1 Docker Compose Setup (Recommended)
The recommended deployment method uses Docker Compose with three services: the NutriAI Express app, a MySQL 8.0 database, and an Ollama instance serving the Qwen 2.5 3B model. A docker-compose.yml file defines all three services with environment variable configuration, volume mounts for data persistence, health checks, and restart policies. The MySQL service mounts a named volume for data persistence across container restarts. The Ollama service exposes port 11434 for the Meal Recommendation AI. Environment variables for DATABASE_URL, OPENAI_API_KEY, SESSION_SECRET, and OLLAMA_BASE_URL are loaded from a .env file on the host.
17.2 Production Deployment with Nginx
For production, Nginx sits in front of the Node.js process, handling SSL termination, static file serving (for the React build and uploaded images), and reverse proxying API requests to Express on port 3000. SSL certificates are obtained free via Let's Encrypt with certbot. PM2 manages the Node.js process with auto-restart on crashes, log rotation, and cluster mode for multi-core utilization. The Nginx configuration includes security headers, Gzip compression, and a 50MB max upload size. MySQL backups are scheduled via a daily cron job using mysqldump with 30-day retention.

18. AI Cost Optimization
One of the most significant advantages of this simplified architecture is the dramatic reduction in infrastructure costs. By eliminating AWS services (S3, ECS, RDS, ElastiCache, CloudWatch, WAF, CloudFront), the total monthly infrastructure cost drops to approximately $5-20/month for a basic VPS. AI costs are the only variable expense, and the architecture minimizes them through intelligent caching and the use of a free, self-hosted model for meal ranking.

18.2 Optimization Strategies
Several additional optimization strategies further reduce costs. First, Vision AI response caching stores recognition results keyed by image perceptual hash (using a simplified hash for speed) in an in-memory Map with 6-hour TTL, so repeated photos of the same meal skip the API call entirely. Second, prompt compression reduces token count by approximately 30% by using abbreviated instructions. Third, batch processing of recognition calls during off-peak hours can leverage potential provider discounts. Fourth, tiered model selection routes simple single-food images to a cheaper, faster model while complex multi-food images receive the full GPT-4o treatment, reducing average cost per call by an estimated 25%.
